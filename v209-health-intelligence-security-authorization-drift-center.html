Security Control Domains

AUTHENTICATION

Review sign-in, session, identity-provider, and token-related configuration against an approved baseline.

AUTHORIZATION

Review role, claim, permission, and access-boundary differences.

RLS

Review row-level security policies, enabled state, grants, and protected data boundaries.

PRIVILEGED ACCESS

Verify that privileged credentials and server-only operations remain outside public browser code.

API ACCESS

Review exposed endpoints and authorization requirements against documented expectations.

FUNCTION SECURITY

Review server-side function authorization, JWT requirements, and privileged execution boundaries.

DATA EXPOSURE

Identify evidence-supported changes that could alter which data a client can read or write.

SECRET HYGIENE

Check that service-role and other privileged secrets are not embedded in client-delivered assets.

Security Drift States

EXPECTED

Observed security configuration matches the verified baseline.

DETECTED

A possible difference has been observed.

VALIDATED

Authoritative evidence confirms the difference.

REVIEWED

A human has documented the interpretation and scope.

Evidence Confidence

VERIFIED

Direct authoritative evidence establishes the security state.

SUPPORTED

Multiple relevant sources support the finding.

PROPOSED

A possible security difference requires validation.

UNKNOWN

Available evidence is insufficient for a reliable security conclusion.

Protected Boundary Review

CLIENT Public browser assets must not contain service-role credentials or other privileged secrets.

RLS Exposed data tables should have an intentional row-level security posture appropriate to their access model.

SERVER Privileged operations belong behind an authorized server-side boundary.

CLAIMS Authorization decisions should rely on trusted claims and server-validated identity context, not user-editable profile fields.

AUDIT Security-sensitive changes should preserve evidence, timestamps, source, and reviewer context.

Critical Guardrail

SECURITY DRIFT ≠ SECURITY BREACH
A configuration difference does not establish that data was exposed, an account was compromised, or a vulnerability was exploited. V209 separates observed configuration, access behavior, evidence, exposure assessment, and incident investigation.

Safety & Platform State

V209 is a review and governance surface. It does not modify authentication, authorization, RLS, grants, secrets, functions, or production configuration. It does not trigger remediation, recovery, notifications, or deletion. No service-role credentials are exposed and no new Edge Function is deployed; the current project function-capacity limit remains respected.
