Identity Provider Domains

PROVIDER REGISTRY

Maintain an explicit record of approved identity providers and their intended use.

REDIRECT ORIGINS

Review callback URLs and redirect origins against the approved application configuration.

SCOPES

Document requested scopes and verify that they are limited to the application's intended identity features.

CONSENT CONTEXT

Record the purpose and evidence for provider consent flows without storing unnecessary provider data.

IDENTITY LINKING

Review how provider identities map to an existing CrowRules account and how ambiguous matches are handled.

CALLBACK VALIDATION

Confirm that authentication callbacks are constrained to approved origins and expected routes.

PROVIDER CREDENTIALS

Keep provider secrets server-side and out of browser-delivered assets.

PROVIDER EVENTS

Correlate provider-related authentication events with identity, access, and incident audit records.

Provider States

APPROVED

Provider configuration matches the documented baseline.

DETECTED

A possible provider or callback difference has been observed.

VALIDATED

Authoritative evidence confirms the difference or configuration state.

REVIEWED

A human has documented scope, evidence, and interpretation.

Evidence Confidence

VERIFIED

Direct authoritative evidence supports the provider finding.

SUPPORTED

Multiple relevant sources support the finding.

PROPOSED

A possible provider difference requires validation.

UNKNOWN

Evidence is insufficient for a reliable conclusion.

OAuth Trust Boundary

PROVIDER A configured identity provider should be explicitly approved before being treated as part of the authentication architecture.

CALLBACK Redirect destinations should be constrained to approved origins and routes.

SCOPE Requested OAuth scopes should be limited to the intended application need.

SECRET Client/provider secrets must remain outside public browser code and logs.

LINKING Provider identity linking should use trusted identity context and avoid ambiguous account merges.

SERVER Sensitive OAuth validation and authorization decisions should occur at a trusted server boundary.

Critical Guardrails

OAUTH CONFIGURATION ≠ ACCOUNT COMPROMISE
A provider or callback difference does not by itself establish unauthorized access, account compromise, or malicious activity. Those conclusions require separate evidence.
PROVIDER SECRET ≠ CLIENT DATA
Provider credentials and sensitive OAuth artifacts should remain server-side. Audit metadata should never contain raw secrets, authorization codes, access tokens, or refresh tokens.

Safety & Platform State

V213 is an audit and governance surface. It does not enable or disable providers, modify redirect URLs, change scopes, link accounts, rotate credentials, or alter authentication configuration. It does not trigger recovery, notifications, or deletion. No service-role credentials are exposed and no new Edge Function is deployed; the current project function-capacity limit remains respected.
