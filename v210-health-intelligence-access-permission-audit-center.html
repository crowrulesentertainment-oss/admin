Access Domains

AUTHENTICATED USERS

Document expected access for signed-in members without assuming every member has identical permissions.

ADMIN OPERATORS

Review privileged administrative access against trusted authorization claims and server-side enforcement.

ANONYMOUS CLIENTS

Document intentionally public read/write boundaries and verify that protected records remain inaccessible.

SERVICE PROCESSES

Track server-side service access separately from browser-visible client permissions.

DATABASE OBJECTS

Review tables, views, functions, grants, and RLS policies as separate permission layers.

EDGE FUNCTIONS

Review authentication requirements and server-side authorization before privileged execution.

STORAGE

Document bucket/object access boundaries and distinguish public assets from protected content.

EXTERNAL INTEGRATIONS

Record only the access scope explicitly supported by integration configuration and evidence.

Audit States

EXPECTED

Observed access matches the approved baseline.

DETECTED

An access or permission difference has been observed.

VALIDATED

Authoritative evidence confirms the observed state.

REVIEWED

A human has documented scope, evidence, and interpretation.

Evidence States

VERIFIED

Direct authoritative evidence supports the access finding.

SUPPORTED

Multiple relevant sources support the finding.

PROPOSED

A possible access difference requires validation.

UNKNOWN

Evidence is insufficient for a reliable conclusion.

Permission Matrix

ACTOR Identify the principal or process without storing unnecessary personal information.

RESOURCE Identify the protected object, service, route, function, bucket, or data domain.

ACTION Distinguish read, insert, update, delete, execute, or other explicitly supported operations.

ENFORCEMENT Record whether access is governed by RLS, grants, function authorization, application checks, or another verified control.

EVIDENCE Preserve the authoritative source and timestamp used for the audit.

Critical Guardrails

ACCESS EVIDENCE ≠ USER INTENT
An observed permission does not establish why it exists or what an actor intended. Audit records should focus on verified authorization state, resource scope, enforcement mechanisms, and evidence.
USER PROFILE DATA ≠ TRUSTED AUTHORIZATION
Authorization decisions should use trusted server-validated identity and claims. User-editable profile fields must not be treated as proof of administrative privilege.

Safety & Platform State

V210 is an audit and governance surface. It does not grant or revoke permissions, change RLS, alter database grants, modify authentication, expose secrets, trigger recovery, or send notifications. No service-role credentials are exposed and no new Edge Function is deployed; the current project function-capacity limit remains respected.
